1. High-level architecture SDK → gateway → queues → workers → Log DB

The gateway is a thin accept-and-enqueue HTTP layer. It never persists telemetry itself: the only durable work on the request path is writing a pg-boss job row. Normalization and storage happen asynchronously in a separate worker process, so a flood of events can be absorbed without blocking or losing data.

Why accept-and-enqueue?

  • Durability is the pg-boss job row. Once enqueueIngestJobs() resolves, events survive a crash of any process.
  • No in-memory buffering, no Redis on this path — the gateway stays cheap enough to absorb floods.
  • Full Zod normalization is worker-side. The gateway does only basic envelope checks (type known, size cap).
  • Backpressure sheds low-priority traffic when queue depth is high, protecting business/enterprise tenants.

Module wiring ingestion.module.ts

  • Reuses the shared Postgres pool and builds a PostgresWriter.
  • Decorates Fastify with postgresWriter; routes construct one IngestionService per scope.
  • All routes are registered under the /api prefix (so /v1/errors is served at /api/v1/errors).
  • onClose disposes rate-limit buckets & usage buffers.

2. The shared ingest pipeline service.processIngest()

Every write route funnels into one private method — the single policy boundary. Typed routes pass their expectedType; the legacy batch passes null. Auth, quota, rate limits, backpressure and queue-priority math are never duplicated per endpoint.

Typed-route enforcement

On a dedicated endpoint (e.g. POST /v1/errors) any event whose type is not the route's family fails the entire batch with INVALID_EVENT_TYPE (400). That is a client-misconfiguration signal — mixed batches must use POST /v1/ingest (expectedType === null), which never sets the constraint.

Partial success vs. hard failure

  • Hard failures (steps 1–5, and INVALID_EVENT_TYPE) throw → mapped to an HTTP error, nothing enqueued.
  • Per-event rejects (unknown type, too large, shed, not-allowed) are collected in errors[]; valid events still enqueue → 202 with rejected > 0.

3. Typed write routes POST /v1/<signal> — the primary SDK transport

Registration is data-driven from TYPED_INGEST_ROUTES (route-table.ts): a single loop registers one dedicated POST per SDK event family. The controller exposes one factory — ingestTyped(type) — that returns a thin handler capturing the type, so there is no hand-written handler per signal. Each handler calls service.ingestTyped(body, apiKey, type) → processIngest(req, type, apiKey).

Design note — /v1/events → message: the SDK's general "events" transport carries custom/captured messages, so it maps to the message family and is a typed route (not a mixed batch). /v1/spans is exposed for direct span streaming even though the SDK config normally advertises spans inside a trace envelope — keeping "each event type has a dedicated POST route" true.

4. Legacy batch & typed sub-paths compatibility only

Older SDK builds keep working through these. New SDKs use the typed routes in §3.

POST /v1/ingest

The only endpoint that accepts a mixed batch (any combination of the 10 event types in one request). Handler controller.ingest → service.ingestBatch → processIngest(req, null, apiKey). Because expectedType is null, the typed-route constraint is never applied — foreign types are simply grouped and enqueued to their own queues.

Typed sub-paths

/v1/ingest/requests, /errors, /logs, /metrics map to ingestRequests / ingestErrors / ingestLogs / ingestMetrics, each a one-line alias that calls ingestTyped(type). Same strict single-type enforcement as the top-level typed routes; retained so previously-issued SDK configs keep resolving.

5. POST /v1/init SDK bootstrap handshake

Called once at SDK startup to fetch runtime config. It does not ingest events.

7. Health routes

GET /v1/health public

Liveness for load balancers. Returns 200 only when Postgres and the pg-boss job table are reachable, else 503 degraded. Honestly reports redis:false — the module is Postgres-only.

GET /v1/ingest/health auth

Operational depth: waiting/active/failed jobs, dead-letter backlog, per-queue snapshot, rate-limiter & quota-cache sizes, backpressure water marks.

8. DLQ admin routes platform-admin only

A job that exhausts retries (or is rejected by validation) lands in ingestion_dead_letter_jobs. These endpoints let operators inspect and requeue it. They require requireAdmin because replay can push arbitrary historical traffic back onto the live queues.

RouteAction
GET /v1/dlqPaginated list of un-replayed dead-letter jobs (bounded offset/limit).
POST /v1/dlq/reprocess/:jobIdReconstruct one job's IngestJobPayload, re-enqueue it, stamp replayed_at/replayed_by. Missing → JOB_NOT_FOUND 404.
POST /v1/dlq/reprocess-allDrain a bounded batch (default 100, max 1000) oldest-first; one bad row is logged and skipped, not fatal.

9. POST /v1/replay admin + project member

Re-enqueues historical, already-stored telemetry through the standard pipeline with replay metadata — e.g. to rebuild a downstream projection.

  • Guards: authenticate + requireAdmin + requireProjectMembershipFromBody.
  • Loads events from the Log DB for [startTime, endTime] (optionally filtered by type), capped by INGESTION_REPLAY_MAX_EVENTS so an operator typo can't flood the queue.
  • Resolves the org's plan tier via getProjectPlanContext (admin path has no API key), groups by type, and enqueues with metadata.replay=true.
  • Idempotent inserts downstream mean re-processed events are de-duplicated and never double-billed.

10. Worker fleet & queues worker-registry.ts · event-processor.ts

A separate worker process registers one pg-boss worker pool per SDK event type. Each delivered job passes a tenant-fairness gate, then the shared EventProcessor validates, de-duplicates, persists, groups errors, and stages billing usage.

Per-job isolation (pg-boss v12)

Handlers receive an array of jobs. Each is processed in its own wrapper and settled individually via perJobResults, so one poisoned job never drags its batch-mates into retry. If every job in the batch fails, the handler throws (whole batch retried).

Fairness & starvation guard

Deferred jobs re-enqueue a copy with deferCount+1 and an aged priority boost; the original completes without processing (nothing lost). After INGESTION_FAIRNESS_MAX_DEFERS the job is processed regardless — no tenant can be starved.

Worker observability endpoints separate node:http server · INGESTION_WORKER_METRICS_PORT (default 9465)

The worker process runs a tiny, dependency-free HTTP server — distinct from the Fastify /api gateway — for scraping and liveness. Best-effort: a bind failure logs a warning and the worker keeps running without metrics.

11. Usage rollup & billing usage-rollup.ts (singleton cron)

Every UsageCounter in the fleet only drains memory into an UNLOGGED staging table. Exactly one cron job rolls staging forward into the durable billing counters, so many worker/API processes don't contend on the billing tables.

Backpressure shedding

  • High water (INGESTION_BACKPRESSURE_HIGH_WATER): shed anything below the business-tier floor — free/starter/growth traffic sheds first.
  • Critical water (INGESTION_BACKPRESSURE_CRITICAL_WATER): only business/enterprise batches of top-urgency types (error/message/cron_checkin) pass.
  • Depth is read from pgboss.job and cached ~1s so the request path stays O(1). Shed events are counted in the response's rejected with reason shed_backpressure.
