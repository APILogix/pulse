# Ingestion DB Update Runbook

This runbook describes what changed for the ingestion optimization work and how to roll an existing environment forward without recreating either database.

## Do We Need To Recreate The Databases?

No.

- Do not recreate the primary database.
- Do not recreate the Log DB.
- Apply the new Log DB migrations.
- Apply the new primary DB hot-path indexes.
- Rebuild existing ingest pg-boss queues only if you need the final `partition=true` queue layout on an already-running environment.

## What Changed

### Log DB changes

- Fixed the error-group trigger contract and removed the typed-event trigger from group tables.
- Replaced the typed-event trigger function with a faster version that avoids unnecessary `jsonb_set()` rewrites.
- Dropped expensive request-table JSONB GIN indexes from the synchronous write path.
- Dropped nonessential high-cardinality request-table btree indexes from the synchronous write path.
- Dropped broad span/log JSONB GIN indexes from the synchronous write path.
- Added a migration that enables notify-enabled ingest queues and partition defaults for new pg-boss ingest queues.

### Primary DB changes

- Added the rotated API-key grace-period lookup index.
- Added the latest live subscription lookup index used on the ingestion auth path.

```sql
CREATE OR REPLACE FUNCTION logdb_sync_typed_event_contract()
RETURNS trigger AS $$
BEGIN
  NEW.occurred_at := COALESCE(NEW.occurred_at, NOW());
  NEW.created_at := COALESCE(NEW.created_at, NEW.ingested_at, NOW());
  NEW.ingested_at := COALESCE(NEW.ingested_at, NEW.created_at);

  IF NEW.metadata IS NULL OR jsonb_typeof(NEW.metadata) <> 'object' THEN
    NEW.metadata := jsonb_build_object('environment', NEW.environment);
  ELSIF NEW.metadata->>'environment' IS DISTINCT FROM NEW.environment THEN
    NEW.metadata := jsonb_set(NEW.metadata, '{environment}', to_jsonb(NEW.environment), true);
  END IF;

  IF NEW.payload IS NULL OR NEW.payload = '{}'::jsonb THEN
    NEW.payload := to_jsonb(NEW) - 'payload' - 'attributes' - 'metadata' - 'ai_response';
  END IF;

  RETURN NEW;
END;
$$ LANGUAGE plpgsql;
```

## Upgrade Order For An Existing Environment

Run these steps in order.

1. Deploy the application code.
2. Apply Log DB migrations.
3. Apply the primary DB hot-path indexes.
4. Restart API and ingestion worker processes.
5. Inspect ingest queue state and rebuild existing queues only if needed.

## Commands

### 1. Apply Log DB migrations

```bash
npm run db:migrate:logdb
```

This applies the new trigger-contract, request-index, and queue-default migrations.

### 2. Apply primary DB hot-path indexes

```bash
npm run ingestion:primary:indexes
```

Use `npm run db:migrate` only if your deployment process already applies all pending primary DB changes together and that is your normal rollout path.

### 3. Restart the application

Restart the API and ingestion worker processes after the code deploy and DB updates so the new queue, profiling, and transaction settings are live.

### 4. Inspect existing ingest queues

```bash
npm run ingestion:queues:rebuild
```

This is a dry run. It tells you whether existing `ingest.*` queues are still using the old non-partitioned layout.

### 5. Rebuild queues only during maintenance

```bash
npm run ingestion:queues:rebuild -- --execute
```

Use this only when:

- workers are stopped
- target ingest queues are drained
- you are in a maintenance window

Do not use `--force-delete-jobs` in production unless you explicitly accept retained-job deletion.

## When Queue Rebuild Is Actually Required

Queue rebuild is not required just to get the current fixes running.

It is required only if you want existing queues to match the final optimized pg-boss layout:

- `partition=true`
- `notify=true`

New queues created after the code and migration update will use the new defaults. Existing queues may remain on the old table layout until rebuilt.

## How To Verify The Update

After rollout, verify these points:

1. Log DB migrations completed successfully.
2. Primary DB indexes exist.
3. Ingestion workers start cleanly.
4. The `uuid = text` error no longer appears for `ingest.error`.
5. `ingestion_profile` logs show low `dbConnectionWaitMs`; if `insertMs` or `commitMs` stay high, the next bottleneck is still Log DB write/commit cost rather than pool wait.

Useful follow-up commands:

```bash
npm run ingestion:db:audit -- --out artifacts/ingestion-db-audit.md
npm run ingestion:admission:summary -- --logs artifacts/ingestion-api.jsonl --out artifacts/ingestion-admission-summary.md
npm run ingestion:worker:summary -- --logs artifacts/ingestion-worker.jsonl --out artifacts/ingestion-worker-summary.md
npm run ingestion:db:runtime:summary -- --runtime artifacts/ingestion-db-runtime.json --out artifacts/ingestion-db-runtime-summary.md
npm run ingestion:triage -- --admission-summary artifacts/ingestion-admission-summary.md --worker-summary artifacts/ingestion-worker-summary.md --db-runtime-summary artifacts/ingestion-db-runtime-summary.md --out artifacts/ingestion-triage-summary.md
```
