# Retry-stable ingestion writes, bounded traces, and Log DB idempotency

This change anchors ingestion timestamps and generated identities to the durable gateway receipt clock, bounds trace trees before database admission, streams spans under PostgreSQL's bind limit, makes queue provisioning fail-fast, and adds log idempotency plus worker-profile reporting. The changed ACK path waits for either the validation DLQ enqueue or the telemetry transaction commit before returning. Five gaps remain across the trace trust boundary, startup rollback, migration correctness/rollout, and profile diagnosis. Watch for: trace `__proto__` fields bypassing pre-checkout validation (**high, confirmed**); organization-wide log conflicts dropping valid cross-project/environment events (**high, confirmed**); a non-concurrent parent index entering the automatic migration stream (**high, likely**); and partial usage-rollup startup surviving a failed registry start (**medium, confirmed**).

**Verdict**: NEEDS_CHANGES

## High-level view

`metadata.receivedAt` now supplies one immutable clock for future-skew clamping, fallback occurrence time, generated identity, error grouping, typed rows, and outbox rows. Invalid clocks fail before pool checkout, rejects are durably sent to the DLQ, and accepted rows commit before pg-boss can receive success.

Trace validation and persistence are iterative, with actual node/depth limits enforced in the normalizer and span INSERTs flushed below 65,535 bind parameters. The clone uses ordinary property assignment, so a JSON-owned `__proto__` key changes the clone's prototype; inherited children evade normalizer counting but become visible to the writer after checkout.

Queue provisioning creates the DLQ before source queues and propagates catalog failures, while concurrent `start()` calls share one attempt. Rollback is not fully retry-safe because `UsageRollup.start()` registers its worker before scheduling, but the registry marks it started only after both operations finish.

The new log uniqueness migration stabilizes retries, but its key is organization-wide while generated identity is project/environment scoped and SDK IDs have no organization-wide uniqueness constraint. The migration is also auto-discovered despite using a non-concurrent parent-table index build, so live application needs an enforced drain or an online partition-index rollout.

Worker summaries expose admission wait separately from pool acquisition for successful and failed transactions. Diagnosis reads only successful admission percentiles, causing a failed-only saturated capture to claim that no bottleneck crossed a threshold.

1. **Trace prototype-key bounds bypass — High, confirmed** — An own JSON `__proto__` key becomes the normalized span's prototype, hiding inherited children from pre-checkout counting while exposing them to the writer. 3. **Blocking log index in automatic migrations — High, likely** — The non-concurrent partitioned-parent index is auto-applied and can block writes to the active log partition. Use an online child-index/attach rollout or enforce a drained, timeout-bounded deployment gate.
4. **Startup rollback leaves registrations behind — Medium, confirmed** — A failed rollup schedule leaves its worker registered, and failed `offWork` cleanup is forgotten before retry. Make component startup atomic and retain/finish failed cleanup before registering replacements.
5. **Failed-only admission pressure is misclassified — Medium, confirmed** — Failed-stage admission p95 is displayed but ignored by diagnosis, which can claim no threshold was crossed. Classify failed admission wait explicitly and add a failed-only test.

## Durable receipt clock and handler completion

```text
pg-boss metadata.receivedAt
        +--> normalizeEvent(nowMs) --> normalized event --> deterministic eventId
        +--> resolveTimestamp(fallbackMs) --> ScopedEvent.occurredAtMs
                                                +--> typed/error rows
                                                +--> error grouping
                                                +--> telemetry outbox
```

`EventProcessor` rejects a missing or malformed receipt clock before admission or pool checkout. Future timestamps clamp with that receipt time rather than `Date.now()`, and the error-specific path consumes the same scoped occurrence time as the generic writer. Validation rejects are awaited into `ingest.dlq-intake`; persisted rows and outbox writes commit before the handler returns. No changed-path ACK-before-durability defect was found.

## Trace clone permits inherited subtrees past the security boundary

The normalizer creates target spans as `{}` and copies non-`children` entries with `current.target[key] = value` at `src/modules/ingestion/pipeline/event-normalizer.ts:377`. For an own enumerable `__proto__` field from JSON, that assignment invokes the target's prototype setter. A direct probe confirmed that the normalized output can have no own `children` property while `output.children` resolves to an attacker-supplied inherited array.

This is a **high-severity, confirmed** bounds bypass. Normalization reads `current.source.children`, where the source still has an ordinary prototype, but persistence later reads `span.children` at `src/modules/ingestion/pipeline/telemetry-writer.ts:1214` and inherited span fields at lines 1112 and 1244. The hidden subtree therefore avoids the pre-checkout count/depth gate, while identity hashing and JSON persistence omit the inherited values that drive relational columns and traversal.

```json
{"type":"trace","traceId":"t","spanCount":1,"rootSpan":{"__proto__":{"spanId":"inherited-root","children":[{"spanId":"hidden-child"}]}}}
```

Use null-prototype clone targets or safe own-property definition, reject dangerous structural keys, and require own properties in the writer. Add a regression built through `JSON.parse`, whose `__proto__` semantics match queue JSON. The reverse-stack traversal and `floor(65535 / 67)` flushing otherwise preserve order and bind limits; the existing test covers a 1,600-row split, but the writer's second bounds check occurs too late to restore the pre-checkout guarantee.

## Usage-rollup registration survives a failed startup attempt

`UsageRollup.start()` awaits `pgboss.work(...)` and then `pgboss.schedule(...)` at `src/modules/ingestion/workers/usage-rollup.ts:102-111`. `WorkerRegistry` sets `rollupStarted = true` only after that method returns (`src/modules/ingestion/workers/worker-registry.ts:236`) and calls `rollup.stop()` only when the flag is true (line 267).

This is a **medium-severity, confirmed** retryability gap: a scheduling failure leaves the already-registered rollup worker alive, so the next `start()` can duplicate the consumer or fail registration. Make rollup startup atomic internally or clean up every attempted start. The cleanup also suppresses `offWork` failures and then clears `registeredQueues` at lines 257-260; it is **likely** that a failed unregister can likewise be forgotten and duplicated on retry. The new test at `worker-registry.test.ts:122` fails during provisioning, before either partial-start case exists.

## Log uniqueness key conflicts with generated identity scope

The migration groups and constrains `(organization_id, event_id, occurred_at)` at `030_events_logs_idempotency.up.sql:21,43`. Generated IDs include project and environment at `src/modules/ingestion/workers/event-processor.ts:82-90`, while SDK IDs are arbitrary bounded strings (`event-normalizer.ts:87`).

This creates a **high-severity, confirmed** silent-loss path. Two projects or environments in one organization can submit valid logs with the same SDK ID and timestamp; the second row hits `ON CONFLICT DO NOTHING` at `telemetry-writer.ts:554`, is counted as a duplicate, and is neither billed nor sent to the outbox. The preflight also labels existing cross-scope rows as duplicates requiring deletion/remediation.

Use the actual project/environment identity scope, or explicitly enforce an organization-wide SDK-ID contract. The migration test currently asserts the organization-only key instead of exercising two valid scopes. Other tables' pre-existing identity choices are outside this review; this migration newly applies the behavior to logs.

## Automatic migration path can block live log ingestion

The migration states that its partitioned-parent index is non-concurrent (`030_events_logs_idempotency.up.sql:40-43`). The Log DB runner auto-discovers `.up.sql` files (`src/shared/logdb/migrations.ts:37-40`), so the build enters the normal migration sequence without a gate.

This is a **high-severity, likely** operational failure unless deployment already guarantees an ingestion drain. Building the unique indexes takes write-conflicting locks on partitions, including the active log partition, and queued DDL can extend the write outage. The comment references a documented live rollout, but no checked-in procedure for this index or child-index attachment path was found.

Move the build out of automatic live migration, provide a concurrently-built child-index/attach rollout, or enforce the drain plus lock/statement timeouts in deployment. The SQL text test cannot verify locking or rollout safety; a disposable PostgreSQL test can cover schema/idempotency, while deployment needs an operational gate.

## Failed-only captures hide admission saturation

The summary records `writeAdmissionWaitMs` in both stage populations but derives its threshold only from `successStages` at `scripts/summarize-ingestion-worker-profiles.ts:344`. A direct failed-only probe produced a 500 ms failed p95 followed by the line-365 fallback that no bottleneck crossed a threshold.

This is a **medium-severity, confirmed** diagnostic contradiction. Classify failed admission wait separately or use a named combined/max population, and add a failed-only fixture; the new test includes a successful 150 ms row, which alone triggers its expected message.

## Validation evidence and untested failure modes

Seven scoped test files passed all 48 tests, and `git diff --check` passed. The summary CLI guard executed correctly. The repository-wide build remains unavailable as a signal because it reports 211 unrelated ambient-global/declaration errors across 74 files; no live PostgreSQL migration was run.

Not tested: JSON `__proto__` input, scheduling failure after rollup worker registration, unregister failure during cleanup, cross-project/environment log identities, live partition-index locking, and failed-only admission pressure.
