# Process-local UsageRollup cleanup without shared schedule deletion

This follow-up removes cluster-global schedule deletion from UsageRollup failure rollback and process shutdown. Local worker registration is retained across failed cleanup and cleared only after `offWork` succeeds. WorkerRegistry preserves the same replacement barrier for its event workers, while repeated rollup schedule provisioning remains a single-row upsert. Watch for: no remaining lifecycle regression in the reviewed paths (**confirmed**).

**Verdict**: APPROVED

## High-level view

UsageRollup now separates shared cron state from process-local worker state. Startup failure and normal stop remove only the local worker, leaving the schedule used by healthy replicas intact.

A rejected `offWork` keeps the registration marked as potentially active. Startup retries cleanup before either `work` or `schedule`, blocking a replacement while the old registration may remain.

WorkerRegistry retains its own failed queue cleanup and invokes UsageRollup cleanup after every attempted rollup start. pg-boss’s `(name, key)` upsert lets all replicas converge on one schedule row.

## Shared usage-rollup schedule survives replica failure and shutdown

Neither failed-start rollback nor `stop()` calls `unschedule`; no `unschedule` call remains under the ingestion workers. Both paths call only `offWork(INGEST_USAGE_ROLLUP_QUEUE, { wait: true })`, which targets workers in the current pg-boss Manager.

pg-boss 12.22 stores schedules under primary key `(name, key)` and implements `schedule` as `INSERT ... ON CONFLICT (name, key) DO UPDATE`. UsageRollup consistently uses its queue name and the default schedule key, so retries and replicas update one shared row.

## Local worker replacement remains behind successful cleanup

UsageRollup sets `workerMayBeRegistered` before awaiting `work`. It clears the flag only after `offWork` resolves; rejection leaves the flag set, and startup preflight aborts before a new `work` or `schedule` call until cleanup succeeds. Normal stop uses the same path, so its failed cleanup is also retained for the next start.

## WorkerRegistry does not orphan the rollup worker

WorkerRegistry records that rollup startup was attempted before awaiting it and calls `rollup.stop()` on rollback even when `rollup.start()` rejects. UsageRollup first attempts its own rollback; the registry then retries it, and any remaining failure stays recorded for UsageRollup’s next preflight.

Attempted event-worker registrations enter `registeredQueues` before `work`, leave only after successful `offWork`, and block provisioning plus replacement on retry when cleanup fails. The rollup queue remains under UsageRollup ownership rather than this set, avoiding conflicting cleanup semantics.

## Focused lifecycle validation

The UsageRollup regression covers schedule failure, repeated rejected `offWork`, blocked replacement, eventual retry, and normal stop while asserting that `unschedule` is never called. WorkerRegistry coverage verifies its replacement barrier. Both focused files passed all 8 tests, and `git diff --check` passed.
