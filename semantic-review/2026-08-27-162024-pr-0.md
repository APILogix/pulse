## Admission status no longer implies a request-wide queue row

**Confirmed:** `IngestionService.processIngest()` calls `enqueueIngestJobs()` only when `acceptedByType.size > 0`, while ingestion handlers return 202 after the service resolves. The package now states that an all-invalid or all-shed request can return 202 with `accepted: 0` and no pg-boss insertion, limiting the enqueue guarantee to events counted in `accepted`.

Basic gateway validation and shedding only produce response errors. The worker-DLQ path begins after a source job exists, so the package consistently separates gateway rejects from `ingest.dlq-intake` and persisted worker-DLQ rows.

## Forward dry-run keeps control-plane effects and skips migration SQL

**Confirmed:** `applyLogDbMigrations()` discovers and filters files before checking out a client, then calls `acquireLogDbMigrationLock(client)`, `ensureMigrationsTable(client)`, and `hasMigrationBeenApplied()` for each selected migration. The dry-run branch returns without reading or executing migration-file SQL.

The database guide, rollout guide, and runbook disclose the possible `CREATE TABLE IF NOT EXISTS logdb_migrations` and ledger reads. They identify `pg_try_advisory_lock` as fail-fast and state that dry-run skips migration 030's drain assertion, duplicate scan, migration-local five-second lock timeout, index DDL, and ledger insert.

## Forward and rollback share one retained-client mutex

**Confirmed:** `LOGDB_MIGRATION_LOCK_KEY` is exported once, and `acquireLogDbMigrationLock()` uses `SELECT pg_try_advisory_lock($1)`. Forward retains its client through migration SQL and ledger recording; rollback retains its client through target lookup, dry-run or down SQL, unlock, and release. Confirmation refusal throws through `finally` rather than exiting inside the protected region.

The contract test covers helper grant/deny behavior and statically checks rollback wiring. Documentation labels concurrent forward/rollback execution `UNVERIFIED`, requires a clone rehearsal, and makes no live-concurrency claim.

## Unlogged usage staging has two documented loss windows

**Confirmed:** `UsageCounter.ensureSchema()` creates `usage_counter_staging` as `UNLOGGED`. The architecture, write-path guide, runbook, forensic report, and roadmap distinguish process death before a successful staging insert from PostgreSQL crash recovery/restart or failover after staging but before durable rollup. Successful staging is not described as fully durable, and recovery behavior remains unmeasured.
