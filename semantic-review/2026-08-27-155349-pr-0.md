# Ingestion v2 implementation and operations evidence package

The new package consolidates the current ingestion architecture, write path, worker lifecycle, schema, performance evidence, rollout procedure, operating guidance, roadmap, and change inventory. It correctly leaves the benchmark unexecuted and the migration-scoped log-duplicate count unknown, but several operational guarantees are stronger than the implementation supports. **Confirmed** mismatches affect HTTP acknowledgement, migration locking, rollback serialization, and billing durability. **Confirmed** omissions also leave the index-removal history and current-working-tree inventory incomplete.

Watch for: **confirmed** zero-accepted 202 responses with no pg-boss insertion; **confirmed** dry-run advisory-lock and ledger-table side effects; **confirmed** rollback execution outside the forward runner’s advisory lock; **confirmed** PostgreSQL-crash loss after usage reaches the `UNLOGGED` staging table; **confirmed** omission of 24 measured prior-phase index removals; **confirmed** evidence-tool changes absent from the “current working-tree diff” catalog.

**Verdict**: NEEDS_CHANGES

## High-level view

**Confirmed:** HTTP 202 is an admission-result status, not an unconditional durable-queue boundary. When gateway checks or backpressure reject every event, the service returns 202 with `accepted: 0` without calling `enqueueIngestJobs()`; those rejects also never enter the worker validation DLQ.

**Confirmed:** Log DB dry-run is not discovery-only. It waits on the session advisory lock, creates the migration ledger if necessary, and queries that ledger; the migration-local five-second lock timeout cannot bound this earlier advisory-lock wait.

**Confirmed:** The rollback command does not participate in the forward runner’s advisory lock. Writer drain does not serialize operator migration commands, so apply and rollback can interleave and leave index state and the ledger inconsistent.

**Confirmed:** Usage is not durable once it reaches `usage_counter_staging`, because that table is `UNLOGGED`. The loss window includes PostgreSQL crash/restart and failover after staging, not only a process crash before staging.

**Confirmed:** Blanket no-removal/retain-all wording omits canonical migrations 025, 028, and 029, whose 24 index drops are confirmed absent by the schema artifact. The supported conclusion is that this forensic session authorized no additional removals.

**Confirmed:** The catalog claims current-working-tree coverage but excludes modified evidence collection, benchmark, diagnosis, EXPLAIN, and validation tooling plus new shared helpers. It must inventory those changes or identify itself as selective.

## HTTP 202 can be returned without durable queue acceptance

**Confirmed:** `IngestionService.processIngest()` calls `enqueueIngestJobs()` only inside `if (acceptedByType.size > 0)`, yet still returns success when the map is empty. `IngestionController.ingest()` and typed handlers send every resolved result with status 202. An all-invalid or all-shed request therefore receives 202, `accepted: 0`, and per-event errors without any pg-boss row.

**Confirmed:** This contradicts the README statement that “HTTP 202 follows successful pg-boss insertion,” the architecture guarantee that 202 means `enqueueIngestJobs()` was awaited, and the runbook principle that 202 means durable queue acceptance. State instead that events counted in `accepted` passed an awaited enqueue and that 202 means admission processing completed, or use a different status when nothing was accepted.

**Confirmed:** Gateway rejects are synchronous response data and never become jobs; only worker normalization rejects are sent to `ingest.dlq-intake`. Qualify the validation-DLQ statements and add all-invalid and all-shed contract tests for the chosen HTTP/disposition behavior.

## Migration dry-run takes a lock and can execute ledger DDL

**Confirmed:** `applyLogDbMigrations()` obtains a client and runs `SELECT pg_advisory_lock($1)` before `ensureMigrationsTable()`, which executes `CREATE TABLE IF NOT EXISTS logdb_migrations`. It then queries the ledger for each selected migration before the dry-run branch skips migration-file SQL. Dry-run avoids the drain assertion, duplicate scan, index DDL, and ledger insert, but not advisory locking, ledger DDL, or ledger reads.

**Confirmed:** The runbook and rollout guide both say dry-run performs discovery/filtering only and takes no lock. Correct those procedures, or return before opening a database session if offline discovery is intended.

**Confirmed:** Migration 030’s `SET LOCAL lock_timeout='5s'` is inside SQL that dry-run never executes and cannot bound the runner’s earlier session advisory lock. Add a bounded advisory-lock policy or warn that dry-run may wait indefinitely behind another runner.

## Rollback is not serialized with canonical migration apply

**Confirmed:** The forward runner holds `LOGDB_MIGRATION_LOCK_KEY` while applying SQL and recording its ledger row. `scripts/logdb-rollback.ts` checks the database and executes the down SQL through `pool.query()` without acquiring that lock; its drain assertion and relation-level lock timeout do not serialize ledger work.

**Confirmed:** After the up transaction commits but before `recordMigration()` inserts the ledger row, rollback can drop the index and delete an absent ledger row, after which the forward runner records migration 030 as applied. Use the same advisory lock on one dedicated rollback client, or impose and verify an equivalent external mutex. Include concurrent apply/rollback in clone rehearsal before calling the procedure safe.

## Billing remains crash-vulnerable after primary staging

**Confirmed:** `UsageCounter.ensureSchema()` creates `usage_counter_staging` as an `UNLOGGED TABLE`. PostgreSQL can truncate unlogged contents during crash recovery, and those rows are unavailable on a promoted standby. Staging survives an API or worker process crash but is not durable across database crash/restart or failover.

**Confirmed:** The architecture calls this “durable usage staging,” while the write-path and roadmap describe loss only before staging. Document process-local and staged-unlogged loss separately, add database restart/failover recovery evidence, and require logged accounting or a replayable transactional source to close the gap.

## No-removal wording hides prior canonical index drops

**Confirmed:** Canonical migrations `025_request_ingestion_hot_path.sql`, `028_request_ingestion_minimal_indexes.sql`, and `029_span_log_ingestion_hot_path.sql` contain 4, 10, and 10 `DROP INDEX` statements. `ingestion-catalog-scope.test.ts` asserts all 24, and `schema-audit-before.json` marks each `REMOVE`, `priorPhase: true`, and `confirmed_absent`.

**Confirmed:** The README says no existing index was selected for removal, the database document says no removal is authorized, and the change catalog says all existing indexes were retained. Scope those claims to additional decisions in this forensic session and disclose the measured prior-phase removals without re-authorizing them.

## The implementation catalog omits the evidence pipeline

**Confirmed:** The catalog says it describes the current working-tree diff, and the README calls it an exact file/function inventory. It omits modified `audit-ingestion-db-schema.ts`, `bench-ingestion-worker.ts`, `diagnose-ingestion-db-runtime.ts`, `explain-ingestion-writes.ts`, and `validate-ingestion-evidence-bundle.ts`, plus new `explain-plan-flatten.ts`, `ingestion-catalog-scope.ts`, `pg-stat-statements.ts`, and tests.

**Confirmed:** These files define evidence scope, matrix planning, runtime capture, plan analysis, and bundle validation. Add their behavior, preserved invariants, coverage, and rollback, or rename the catalog as a selected production-path inventory.

**Confirmed:** The advertised 9-file, 61-test suite passed and `git diff --check` found no whitespace errors, but this coverage does not exercise zero-accepted HTTP status, dry-run side effects, apply/rollback concurrency, or PostgreSQL restart behavior for unlogged staging.
