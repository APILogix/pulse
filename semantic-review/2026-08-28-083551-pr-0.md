# Automatic/operator migration split fixes ingestion-worker startup crash on migration 030

Migration 030 (`030_events_logs_idempotency.up.sql`) raises `55000` on any populated `events_logs` table without a session-level drain assertion, and the ingestion worker previously ran the shared migration runner in a single mode that executed every pending file at startup, so a populated production table crashed the process before it could serve traffic. The fix adds an `executionMode` of `automatic` versus `operator` on `applyLogDbMigrations()`, tags 030 with a `codex-logdb-migration: requires-operator-drain` marker, and has worker startup defer any marked file (no SQL, no ledger row, warn and continue) while `scripts/migrate-logdb.ts` keeps running in `operator` mode with every existing safety gate intact.

Watch for: **confirmed** — default (no-`executionMode`) callers of `applyLogDbMigrations()`, including `test/integration/alerting-runtime-repository.test.ts`, still run in `operator` mode and will re-trigger the `55000` failure the moment their target table is non-empty; safe today only because that caller always targets a fresh scratch database. **confirmed** — the log retry idempotency guard remains absent until an operator explicitly runs the migration; every worker startup logs a deferral warning until then.

**Verdict**: APPROVED

## High-level view

`executionMode` is threaded through `applyOneMigration()`. In `automatic` mode, the function reads the migration file to classify it, and if it's marked `requires-operator-drain` returns a `deferred` status without executing the file's SQL or writing to `logdb_migrations`. In `operator` mode the marker is ignored and the migration's own SQL-level gates (`55000` drain check, `23505` duplicate check) remain authoritative.

The worker only calls with `executionMode: 'automatic'`. A deferral logs a warning and falls through to `startPgBoss()` and worker registration — startup is not aborted. A migration that genuinely fails (bad SQL, `55000`/`23505` raised during an operator-mode execution, connection failure) still propagates out of `applyOneMigration()`, increments `failed`, and re-throws, so `start()` rejects and the process still crashes on a real failure exactly as before; only the "deferred because marked" case is a soft continuation.

`scripts/migrate-logdb.ts` passes `executionMode: 'operator'` and reports `deferred` separately in its summary line, so an operator running it against a populated table still hits the original `55000`/`23505` protections unchanged. Nothing sets the `pulse.events_logs_identity_drain_confirmed` GUC automatically anywhere in the diff, and neither migration direction deletes or otherwise touches existing telemetry rows.

`deferred` is counted as a subset of `skipped`, not a sibling total, matching the contract test's `{ found: 1, applied: 0, skipped: 1, deferred: 1, failed: 0 }` (automatic) versus `{ found: 1, applied: 1, skipped: 0, deferred: 0, failed: 0 }` (operator) assertions. The already-applied and dry-run checks run before the deferral branch, so neither status gets reclassified as deferred.

Documentation (runbook, worker-architecture, live-db-rollout guide, README, implementation catalog) matches the code: startup order now lists apply/defer/warn/continue, and the runbook states that seeing the old `55000` fatal after this build ships means the process is still running stale `dist` or an operator-mode invocation.

## Marker detection and file classification

`requiresOperatorDrain(sql)` is a regex test (`/^--\s*codex-logdb-migration:\s*requires-operator-drain\b/im`) run against file contents already read from disk. It only runs when `dryRun` is false and the migration hasn't already been applied, so dry-run still never reads migration-file SQL, and an already-applied file is never re-read or re-classified. The marker in 030's `.up.sql` sits on its own line directly after `BEGIN;`, matching the contract test's `/^BEGIN;\s*--\s*codex-logdb-migration:\s*requires-operator-drain\b/i` assertion.

## Advisory lock and loop continuation after a deferral

The lock is acquired once per `applyLogDbMigrations()` call and released in `finally` regardless of outcome, unchanged from before this diff. Inside the loop, a `deferred` outcome takes the same non-throwing path as `already-applied` or `dry-run`, so the loop proceeds to the next migration file — deferral of one file does not block other files from being applied in the same automatic-mode pass.

## Fresh-database behavior

On an empty `events_logs` table, the `DO $$ ... $$` block's `table_has_rows` check short-circuits and both the drain assertion and duplicate scan are skipped, so operator-mode execution against a fresh database succeeds without the GUC set. This is why the no-options integration test caller flagged above doesn't presently trip the issue.
